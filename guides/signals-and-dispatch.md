# Signals and Dispatch
<!-- covers: jido_signal.guides.signals_and_dispatch -->

A Signal describes an event. Dispatch sends that Signal through an adapter.
Define the event contract first, then choose the destination and delivery mode.
Read [Core Concepts](concepts.md) for the difference between routing, dispatch,
and Bus publication.

## Signal Structure

Signals implement the CloudEvents 1.0 specification:

```elixir
# Basic signal
# Positional constructor (type, data, attrs)
{:ok, signal} =
  Jido.Signal.new("user.created", %{"user_id" => "123", "email" => "user@example.com"},
    source: "/auth/service"
  )

# Map constructor
{:ok, signal} =
  Jido.Signal.new(%{
    type: "user.created",
    source: "/auth/service",
    data: %{"user_id" => "123", "email" => "user@example.com"}
  })
```

The resulting Signal has these fields:

| Field | Value in this example |
| --- | --- |
| `id` | Generated UUID7 |
| `specversion` | `"1.0"` |
| `type` | `"user.created"` |
| `source` | `"/auth/service"` |
| `data` | The supplied string-key map |
| `time` | `nil`, unless supplied |
| `datacontenttype` | `nil`, unless supplied |
| `extensions` | Flat CloudEvents context attributes |

JSON-safe data uses the wire `data` field. Non-UTF-8 binary data becomes Base64
text in `data_base64`. JSON serialization rejects other Erlang-only values.
`datacontenttype` describes the data; it does not convert it.

## Signal IDs

Jido generates a UUID7 when no ID is supplied. External IDs can be other
non-empty strings that meet the envelope's character rules. UUID7 utilities
accept only UUID7 values.

A UUID7 contains a Unix millisecond timestamp. Values from different
milliseconds sort by time. Values from the same millisecond have random order.

```elixir
# IDs are auto-generated by Signal.new
{:ok, signal} = Jido.Signal.new("user.created", %{"user_id" => "123"}, source: "/auth")

# Generate IDs manually
id = Jido.Signal.ID.generate!()

# Extract timestamp from ID
timestamp = Jido.Signal.ID.extract_timestamp(signal.id)
# Unix milliseconds from the generated ID

# Compare complete UUID7 values
:eq = Jido.Signal.ID.compare(id, id)
```

### ID Utilities

| Function | Description |
|----------|-------------|
| `Jido.Signal.ID.generate!/0` | Generate a new UUID7 string |
| `Jido.Signal.ID.generate/0` | Generate UUID7 with timestamp tuple |
| `Jido.Signal.ID.extract_timestamp/1` | Get Unix milliseconds from ID |
| `Jido.Signal.ID.compare/2` | Compare complete UUID7 values (`:lt`, `:eq`, `:gt`) |
| `Jido.Signal.ID.valid?/1` | Validate UUID7 format |

## Dispatch Adapters

Dispatch delivers Signals through validated `{adapter, options}` targets.
It does not require every application effect to use a Signal. Actions can
perform direct I/O when the caller needs an immediate result.

### PID Adapter

Direct process delivery:

```elixir
# Async delivery (fire-and-forget)
config = {:pid, [target: pid, delivery_mode: :async]}
:ok = Jido.Signal.Dispatch.dispatch(signal, config)

# Sync delivery (wait for the GenServer reply)
config = {:pid, target: pid, delivery_mode: :sync, timeout: 10_000}
```

Sync delivery calls `GenServer.call/3` with `{:signal, signal}` by default.
The target must handle that call. An `{:error, reason}` reply becomes a
dispatch error; any other reply becomes `:ok`. Dispatch discards successful
reply data. A call to the calling process itself returns an error.

Async delivery confirms only that the message was sent. It does not confirm
processing or provide redelivery.

### Named Process Adapter

PID and named-process targets must use a local PID or a local registered name.
The timeout must be an integer from 1 to 4,294,967,295 milliseconds. This is the
[OTP receive timeout limit](https://www.erlang.org/docs/27/system/expressions.html#receive).

Delivery to registered processes uses the same local-process adapter as PID
delivery:

```elixir
config =
  {:pid,
   [
     target: {:name, :my_server},
     delivery_mode: :async
   ]}
```

The v2 `:named` adapter name is still accepted as a compatibility alias. Use
`:pid` for new code.

### PubSub Adapter

Phoenix.PubSub broadcast. This adapter is optional; add `{:phoenix_pubsub, "~> 2.1"}`
to your application dependencies before using `:pubsub` dispatch.

```elixir
config =
  {:pubsub,
   [
     target: :my_app_pubsub,
     topic: "events"
   ]}
```

### HTTP Adapter

HTTP endpoint delivery:

```elixir
config =
  {:http,
   [
     url: "https://api.example.com/events",
     headers: [{"x-api-key", "secret"}],
     timeout: 5000
   ]}
```

HTTP delivery requires JSON-safe data with string map keys. Setting
`datacontenttype` does not convert atom keys or other Erlang values. See
[Serialization](serialization.md#signal-data).

The HTTP adapter uses OTP `:httpc`; it does not need Req or another HTTP client.
It sends structured CloudEvents JSON and does not follow redirects. Dispatch
does not add a retry loop. OTP `:httpc` can honor `Retry-After` on a 503
response, and OTP 27 has no option to disable that client behavior. Use a
custom adapter when strict single-attempt delivery is required.

Treat each URL as trusted application configuration. The built-in adapter
permits private network targets and does not protect against DNS rebinding.
OTP 27 `:httpc` has no response body size limit for these requests. Use a
custom adapter for untrusted targets or a strict response size limit.

The HTTP target accepts only `url`, `headers`, and `timeout`. Its content type,
TLS verification, and HTTP method cannot be changed. Use a custom Dispatch
adapter when an integration needs request signing, another method, custom TLS
policy, or response data. The v3 package does not include the old proprietary
Webhook adapter.

## Dispatch Execution

### Synchronous Dispatch

Dispatch waits for each adapter call and handles targets in list order.
For async PID and PubSub targets, completion means send or broadcast completion,
not consumer processing:

```elixir
:ok = Jido.Signal.Dispatch.dispatch(signal, config)
```

To run delivery asynchronously, start the Task in the calling application:

```elixir
task = Task.async(fn -> Jido.Signal.Dispatch.dispatch(signal, config) end)
result = Task.await(task)
```

### Multiple Destinations

Send to multiple adapters:

```elixir
configs = [
  {:pubsub, [target: :pubsub, topic: "events"]},
  {:logger, [level: :info]},
  {:http, [url: "https://webhook.example.com"]}
]

:ok = Jido.Signal.Dispatch.dispatch(signal, configs)
```

## Custom Signal Types

Define structured signal types:

```elixir
defmodule UserCreatedSignal do
  use Jido.Signal,
    type: "user.created",
    default_source: "/auth/service",
    datacontenttype: "application/json",
    schema:
      Zoi.object(%{
        "user_id" => Zoi.string(),
        "email" => Zoi.string(),
        "name" => Zoi.string() |> Zoi.optional()
      })
end

# Usage
{:ok, signal} =
  UserCreatedSignal.new(%{
    "user_id" => "123",
    "email" => "user@example.com"
  })

# Override defaults
{:ok, signal} =
  UserCreatedSignal.new(
    %{"user_id" => "123", "email" => "user@example.com"},
    source: "/different/source"
  )

# Dispatch separately:
Jido.Signal.Dispatch.dispatch(signal, {:pubsub, [target: :pubsub, topic: "user-events"]})
```

Zoi is the schema format for custom Signals. A schema can accept any Signal
data value. `validate_data/1` and `new/2` return Zoi validation errors without
a Jido wrapper. Schemas must be static module data. Use named MFA values for
all Zoi callbacks:

```elixir
defmodule MyApp.SignalChecks do
  def not_blank(value, _opts) do
    if String.trim(value) == "", do: {:error, "cannot be blank"}, else: :ok
  end
end

schema = Zoi.string() |> Zoi.refine({MyApp.SignalChecks, :not_blank, []})
```

Anonymous callbacks and lazy schemas are rejected at compile time.

### Schema Validation

Custom signals validate data against schema:

```elixir
# Valid
{:ok, signal} =
  UserCreatedSignal.new(%{
    "user_id" => "123",
    "email" => "user@example.com"
  })

# Invalid - missing required field
{:error, reason} =
  UserCreatedSignal.new(%{
    "user_id" => "123"
    # email is required
  })
```

## Error Handling

### Validation Errors

```elixir
# Invalid dispatch config
{:error, reason} = Jido.Signal.Dispatch.validate_opts({:invalid, []})

# Invalid signal data
# missing type and source
{:error, reason} = Jido.Signal.new(%{})
```

### Delivery Errors

Dispatch returns adapter error reasons by default. These can be atoms,
tuples, or validation text. Enable structured errors with
`config :jido_signal, normalize_dispatch_errors: true`. Delivery errors then
use `Jido.Signal.Error.DispatchError`; configuration errors use
`Jido.Signal.Error.InvalidInputError`.

```elixir
# Process not alive (returns raw atom by default)
{:error, :process_not_alive} =
  Jido.Signal.Dispatch.dispatch(signal, {:pid, [target: dead_pid]})

# If the HTTP endpoint responds with 503 (example outcome)
{:error, {:http_status, 503}} =
  Jido.Signal.Dispatch.dispatch(signal, {:http, [url: "https://api.example.com/events"]})
```

### Multiple Target Errors

```elixir
# Some failures
{:error, reasons} = Jido.Signal.Dispatch.dispatch(signal, configs)
```

A target list collects returned errors in target order and continues delivery.
If a custom adapter raises, throws, or exits, Dispatch emits exception telemetry
and propagates the fault. Later targets are not called.

Dispatch does not own retries, concurrency, Tasks, or circuit breakers. Add these
policies at the application boundary where ownership and failure handling are clear.
